## Executive summary

The audit found two P0 pipeline correctness defects:

1. The UI and `/api/runs` preserve the user's full task string, and the task analyst prompt includes the full goal, but Coding receives only `TaskBrief.codexInstruction`. The original task is written to `input.json` and later rendered in Coding Markdown reports, so the report can show the complete UI task while Codex receives a summarized or transformed TaskBrief instruction. Markdown headings and BEGIN/END blocks can therefore be lost by the Task Analyst before Coding.
2. Structured `diffCheck` evidence is recorded in `coding-result.json` but is not passed to Review because `reviewChange` receives a `codingResult` object that explicitly omits `diffCheck`. Review Markdown can display `diffCheck` later during `writeSessionReport`, after the model has already made the review decision. This explains PASS evidence in generated reports and UNCERTAIN criteria in the model-authored review result.

Additional P1 findings:

- Per-attempt Markdown reports are generated by `writeSessionReport`/`writeFinalReport`, not immediately when each step becomes terminal. Timeline report selection can therefore fall back to raw JSON until final export or run-exit report generation occurs.
- The Final timeline row exists only when `final-result.json` exists; `writeSessionReport` alone writes `FINAL_REPORT.md` and per-step reports but does not create a final row unless a final result artifact already exists.
- Existing tests encode a mixture of obsolete expectations, ambiguous contracts, and genuine production/report lifecycle gaps. The audit did not edit tests.

Concrete invariant proposed:

> The full original UI task must be passed verbatim to every Coding attempt, including rework attempts, under an explicit `Original user task (verbatim)` section. Derived `TaskBrief` objective, acceptance criteria, non-goals, and rework findings may be added as separate structured sections, but they must never replace, summarize, truncate, parse, or transform the original task.

| stage | source file/function | evidence included? | details |

| `coding-result.json.diffCheck` | `src/cli/run.ts` after Coding, `src/codingWorker.ts` `writeCodingArtifacts()` | Yes | Coordinator collects `git diff --check` and writes status, command, exitCode, stdout, stderr into `coding-result.json` |

Proposed precedence:

1. Structured coordinator evidence (`coding-result.json.diffCheck`, workspace boundary/runtime metadata, changed-file list).
2. Validation evidence (`validation-report.json` commands/results).
3. Workspace evidence (`workspace.diff`, `workspace-status.txt`, changed files).
4. Codex natural-language claims (`CodingResult.finalResponse`).

## Report lifecycle

| event | source artifact | Markdown report | creation time | timeline path |
|---|---|---|---|---|
| Coding attempt terminal | `coding-result.json`, `workspace.diff`, `workspace-status.txt`, `attempt.json` | `coding-report.md` | Currently only when `writeSessionReport`/`writeFinalReport` calls `ensureStepResultArtifacts`; not immediately at coding terminal | Timeline prefers `coding-report.md` if it exists, otherwise falls back to `coding-result.json` |
| Validation terminal | `validation-report.json`, updated attempt artifacts | `validation-report.md` | Currently only during report export/final write | Timeline prefers `validation-report.md` if it exists, otherwise falls back to `validation-report.json` |
| Review terminal | `review-report.json` | `review-report.md` | Currently only during report export/final write | Timeline prefers `review-report.md` if it exists, otherwise falls back to `review-report.json` or `review-package.md` |
| Final terminal result | `final-result.json` | `FINAL_REPORT.md` | `writeFinalResult` creates final JSON; `writeSessionReport` later writes final Markdown | Timeline appends Final only if `final-result.json` exists, with report path `FINAL_REPORT.md` |
| UI child process exits | existing run artifacts | all per-step reports + `FINAL_REPORT.md` | `src/uiApi.ts` child `exit` handler calls `writeSessionReport` | After this, report buttons should resolve Markdown if final result and attempts exist |
| Manual final export | existing run artifacts | all per-step reports + `FINAL_REPORT.md` | `GET /api/runs/:id/final-export` calls `writeSessionReport` | Existing rows begin resolving Markdown on next timeline refresh |
| Stop run | `.ui-stopped`, existing artifacts | best-effort `FINAL_REPORT.md` | `stopRun()` calls `writeSessionReport`, but does not itself create `final-result.json` | Final row still depends on whether `final-result.json` exists |

Findings:

- Per-attempt Markdown reports do not exist immediately when each step becomes terminal unless final/report export has already run.
- Timeline can temporarily fall back to raw JSON by design because `reportCandidates()` includes JSON fallbacks after Markdown candidates.
- Old attempt reports are not overwritten by later attempts because per-attempt reports are written inside each attempt directory. Aggregate legacy reports (`01_CODEX_REPORT.md`, `02_VALIDATION_REPORT.md`, `03_REVIEW_REPORT.md`) are overwritten and summarize the latest attempt bundle.
- The Final row condition is the presence of `final-result.json`, not `FINAL_REPORT.md` alone.
- `writeSessionReport` should remain a report exporter and should not silently invent terminal state. If UI/tests require a Final row, they should ensure `final-result.json` exists or production should create it at the terminal lifecycle boundary.

## Typography findings

- body: `12px/1.25` monospace.
- panel headings: `h2` 12px, `h3` 11px.

Served UI findings:

- `src/uiServer.ts` serves static assets directly from resolved `src/ui` or built `ui` directories with `content-type` headers but no cache-control header.
- There is no observed asset fingerprinting or explicit browser cache busting.
- If a browser already cached `/app.css`, lack of cache-control may make stale CSS plausible depending browser/session behavior.
- If served fresh, the code is active; the likely user perception issue is insufficient visual reduction and unchanged layout geometry, not missing CSS.

Recommended target values for a future UI-polish checkpoint, not implemented here:

- body: 11px/1.2.

## Recommended implementation order

### P0 critical pipeline correctness

1. Task integrity invariant:
   - Add original task to Coding input/prompt as an explicit verbatim block.
   - Keep TaskBrief fields as derived sections.
   - Apply same invariant to rework prompts.
   - Persist enough prompt metadata in `coding-result.json` or runtime manifest to audit what Coding actually received.
2. Review evidence precedence:
   - Include `diffCheck` in `ReviewerInput` for initial and rework review calls.
   - Update Review prompt to name status, command, exitCode, stdout, stderr and precedence.
   - Add deterministic tests where `diffCheck.status=PASS` prevents UNCERTAIN for the diff-check criterion when no conflicting evidence exists.

### P1 contract/report correctness

3. Decide and implement report lifecycle contract:
   - If per-attempt Markdown must exist when steps become terminal, generate it at each terminal boundary.
   - Otherwise update UI/tests/handoff language to explicitly allow JSON fallback until final export.
4. Clarify Final row contract:
   - Final row should be tied to `final-result.json` terminal artifact.
   - `writeSessionReport` should not create terminal state unless renamed or explicitly contracted to do so.

### P2 test consistency

5. Update tests only after P0/P1 contracts are approved:
   - Remove obsolete legacy report path expectations from chronological rows.
   - Ensure fixtures create final-result artifacts when expecting Final rows.
   - Avoid brittle exact CSS assertions unless target values are part of an approved contract.

### P3 UI polish

6. Typography/browser-cache polish:
   - Tune sizes and dimensions together.
   - Add cache-control or versioning for UI assets in development.
7. Icon/motion polish:
   - Add reduced-motion handling and refine SVGs if desired.
